# Deployment Notes

This file is the deploy source of truth for this repo.

## Dashboard Frontend

The dashboard is a Next.js static export deployed through Firebase Hosting.

Firebase config:
- Project: `timeline-automated-scraper`
- Hosting public folder: `dashboard/out`
- Config file: `firebase.json`

Deploy flow:

```powershell
cd dashboard
npm run lint
npm run build
cd ..
firebase deploy --only hosting --project timeline-automated-scraper
```

Important: run `firebase deploy` from the repo root after `cd ..`, not from inside `dashboard/`. The root `firebase.json` is what points Firebase Hosting at `dashboard/out`.

If the Firebase CLI is not installed globally:

```powershell
npx firebase-tools deploy --only hosting --project timeline-automated-scraper
```

Important: dashboard env values are baked during `npm run build`. Check `dashboard/.env.local` before building, especially:

```text
NEXT_PUBLIC_AUTH_API_BASE_URL
NEXT_PUBLIC_FIREBASE_API_KEY
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN
NEXT_PUBLIC_FIREBASE_PROJECT_ID
NEXT_PUBLIC_FIREBASE_APP_ID
```

Current important value:

```text
NEXT_PUBLIC_AUTH_API_BASE_URL=https://hanifmhndra-timeline-scele-auth.hf.space
```

Local preview should use webpack:

```powershell
cd dashboard
npm run dev:webpack -- -p 3001
```

Avoid normal `npm run dev` unless needed; it has been laggy/problematic in this workspace.

Do not edit `dashboard/out` manually. It is generated by `npm run build` and will be overwritten.

If a deployed static asset such as a theme background appears unchanged while local preview is correct, hard refresh the browser (`Ctrl+Shift+R`). If it is still cached, bump the asset query string in `dashboard/src/app/globals.css`, rebuild, and redeploy.

### Academic-year course gate

The live backend filters SCELE dashboard course links before opening any course
page. Using `Asia/Jakarta`, January-June selects `(year-1)/year` and
July-December selects `year/(year+1)`. A course title must contain that active
academic year using a full or supported abbreviated label. Old, future, and
unlabelled courses are skipped; if none remain, the scrape fails safely and the
previous timeline is preserved.

The root local scraper applies the same rule to `config/courses.json`, where
each entry must declare `academicYear`. Old cached HTML is ignored during local
extraction and is not deleted automatically.

If `timeline-scele-auth/` is already clean and up to date, there is nothing to redeploy.

## Legacy Cloud Run Copy

`cloud-run-auth/` is a Google Cloud Run version of the auth/scrape backend. It is currently not the backend used by the dashboard, because the dashboard points to the Hugging Face Space URL.

Do not deploy or modify Cloud Run unless explicitly requested.

If Cloud Run is revived later, the dashboard must be rebuilt with `NEXT_PUBLIC_AUTH_API_BASE_URL` set to the Cloud Run service URL, then redeployed to Firebase Hosting.

Example Cloud Run deploy pattern, only if intentionally reviving Cloud Run:

```powershell
cd cloud-run-auth
gcloud config set project timeline-automated-scraper
gcloud builds submit --tag gcr.io/timeline-automated-scraper/timeline-scele-auth
gcloud run deploy timeline-scele-auth `
  --image gcr.io/timeline-automated-scraper/timeline-scele-auth `
  --platform managed `
  --region asia-southeast2 `
  --port 7860 `
  --allow-unauthenticated
```

Check actual service name and region first:

```powershell
gcloud run services list --platform managed
```

## What Deploys What

- Firebase Hosting deploy updates only the static dashboard from `dashboard/out`.
- Hugging Face Space update changes live `/auth/login`, `/auth/logout`,
  `/scrape`, `/activities`, `/gradebooks` (termasuk `/imports`),
  `/task-state/completed`, and `/healthz` backend behavior.
- Deploy the backend before a dashboard that calls a new endpoint. The
  dashboard's "Tandai selesai" uses `/task-state/completed`; against an older
  backend each toggle is rolled back with a warning.
- Cloud Run deploy only matters if `NEXT_PUBLIC_AUTH_API_BASE_URL` is changed to a Cloud Run URL and the dashboard is rebuilt/redeployed.

## Phase 6 Configuration Model

The root local scraper uses its checked-in course config and local Playwright
session workflow; it is not a hosted deployment target. The production backend
is still `timeline-scele-auth/` on Hugging Face, and `cloud-run-auth/` remains
legacy and unchanged.

Backend startup requires explicit `APP_ENV`. Docker sets it to `production`;
Hugging Face must provide production project/service-account/key/origins. Use
`timeline-scele-auth/.env.example` as the complete inventory: identity/build
metadata, Firebase/session/CORS, scrape coordination/retention, grade/import/
study limits, request timeouts, shutdown, proxy, and three rate limits. Numeric
values and origins are fully validated. Production rejects demo/test project
IDs; test/staging rejects the known production project unless an exceptional
explicit override is reviewed. Do not set `ALLOW_PRODUCTION_TARGETS=true` in
normal development, test, or staging.

Dashboard public build variables are listed in `dashboard/.env.example`.
Firebase web config and `NEXT_PUBLIC_AUTH_API_BASE_URL` are baked into the
static export and must all target the same environment. `NEXT_PUBLIC_APP_VERSION`
is optional display/build metadata. Firebase public API keys are not service
account secrets, but still must not grant authorization by themselves.

`GET /health` is dependency-free liveness; `/healthz` is its compatibility
alias. `GET /ready` checks configuration, Firebase Admin/Firestore client
initialization, and catalogs without queries or external calls. Both are safe
for platform probes. Private responses remain `no-store`.

## Local production-readiness validation

The full preflight is read-only with respect to source/external systems. It may
regenerate ignored dashboard build artifacts, starts/stops a local emulator,
and performs no deploy, Firestore production write, SCELE login, or scrape.

```powershell
node scripts/preflight.mjs
npm run preflight:staging
```

The staging command additionally requires the uncommitted
`timeline-scele-auth/.env.staging` and `dashboard/.env.staging` files and an
explicit `staging` Firebase alias/Hosting target. It prints `STAGING_BLOCKED`
until every target cross-check is safe. Use the committed `.env.staging.example`
templates; never rename the production `.env.local` into a staging build. On a
safe mapping it invokes `npm run dashboard:build:staging`, which injects the
reviewed public staging variables and rejects an artifact containing known
production identifiers.

Individual checks:

```powershell
npm test
npm run test:emulator
node scripts/secret-scan.mjs
cd dashboard
npm run lint
npx tsc --noEmit
npm run build
cd ..\timeline-scele-auth
npm test
npm run check:config
npm run check:catalog
```

Firestore emulator is pinned to `127.0.0.1:8181` and project
`demo-scele-timeline`; the existing service on port 8080 is not touched.
On Windows, the repository runner also verifies and terminates only its own
demo Java emulator if Firebase CLI leaves it behind after a successful run.

## Backend staging checklist

1. Create/use the separate resources in `docs/STAGING.md`; verify every env and
   secret name without printing values.
2. Run the complete preflight locally.
3. Deploy the backend revision to the staging Hugging Face Space only.
4. Check staging `/health`, then `/ready`.
5. Deploy reviewed Rules and indexes to the staging Firebase project only.
6. Re-run demo-project emulator/rules tests locally.
7. Set short-lived isolated token variables and run `scripts/smoke-staging.mjs`
   with `ALLOW_STAGING_SMOKE=true`.
8. Review structured logs/metrics for request IDs, failures, and redaction.
9. Perform the manual matrix in `docs/STAGING.md`.
10. Obtain separate explicit consent before any one-shot SCELE staging smoke.

## Dashboard staging checklist

1. Set all staging Firebase public variables and staging API origin in the
   ignored `dashboard/.env.staging` file.
2. Run lint/TypeScript through preflight and build only with
   `npm run dashboard:build:staging`; a normal Next build may load `.env.local`.
3. Deploy to the staging Hosting target, never the production target.
4. Verify custom-token auth and auth-expiry behavior.
5. Verify Timeline, Nilai, and Belajar navigation and copyable request IDs.
